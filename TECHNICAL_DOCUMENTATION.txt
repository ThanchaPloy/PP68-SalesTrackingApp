2.5 ชั้นที่ 5 — Network
--------------------------------------------------------------------------------
ที่อยู่ : di/NetworkModule.kt, data/remote/*.kt

มี Retrofit สามตัวใช้ OkHttpClient ร่วมกันหนึ่งตัว
  ApiService        -> BuildConfig.POSTGREST_URL   (API ธุรกิจทั้งหมด)
  AuthService       -> BuildConfig.BASE_AUTH_URL   (login/register/setup)
  UploadApiService  -> BuildConfig.UPLOAD_URL      (อัปโหลดรูป)
ปัจจุบันทั้งสามชี้ไป https://api-ploy.cskmitl.com/ เหมือนกัน

สิ่งที่ซ่อนอยู่ใน OkHttpClient ตัวเดียวนี้ (ทุกคำขอของแอปผ่านตรงนี้หมด):
  1. ใส่ Authorization: Bearer <token> ให้ทุกคำขอ ยกเว้น login/register
  2. ใส่ Content-Type: application/json ยกเว้น multipart (ไม่งั้นรูปพัง)
  3. ใส่ Accept-Profile / Content-Profile (มรดกยุค PostgREST ฝั่ง server ไม่ได้ใช้)
  4. เจอ 401 จาก endpoint ที่ต้อง auth = ถือว่า session หมดอายุ -> ล้าง token
     แล้วแจ้ง TokenManager.sessionExpired ซึ่ง NavGraph ฟังอยู่ แล้วเด้งไปหน้า Login
     (ยกเว้น login/register/change-password/complete-initial-setup ซึ่ง 401
      แปลว่า "รหัสผ่านผิด" คนละความหมาย)
  5. อ่าน header Date ของทุก response เก็บเป็น "เวลาอ้างอิงจากเซิร์ฟเวอร์"
     (ดูหัวข้อ 4.6)
  6. ถ้า response ไม่ใช่ 2xx จะบันทึกลงไฟล์ diagnostics (ดูหัวข้อ 6)

Gson ถูกตั้งค่าพิเศษ: ฟิลด์ที่ "ไม่มี" @SerializedName จะไม่ถูกส่งขึ้น server เลย
นี่คือวิธีกันไม่ให้คอลัมน์ local-only (is_synced, projectName, locationName ฯลฯ)
หลุดขึ้นไป ผลข้างเคียงคือการเติม @SerializedName ให้ฟิลด์ไหนก็ตาม = เริ่มส่งขึ้น
server ทันที ต้องคิดก่อนทุกครั้ง

ข้อยกเว้นที่ตั้งใจ: SalesActivity.companyName มี @SerializedName("customer_name")
เพื่อ "อ่าน" ชื่อบริษัทที่ server แนบมากับนัดหมาย และมันไม่หลุดขึ้น server เพราะทุก
เส้นทางที่เขียนนัดหมายประกอบ Map เอง ไม่ได้ปล่อย entity ให้ Gson แปลง

3.1 มรดกจาก PostgREST (อ่านข้อนี้ก่อนเสมอ)
--------------------------------------------------------------------------------
ระบบนี้เคยใช้ PostgREST เป็น backend แล้วถูกเขียนใหม่เป็น Ktor โดย "จงใจเลียนแบบ
รูปแบบสายของ PostgREST" เพื่อให้แอป Android ไม่ต้องแก้ นี่อธิบายเกือบทุกอย่างที่ดู
แปลกในชั้น network:

  * ตัวกรองเป็น query param ที่มี operator นำหน้า
        ?cust_id=eq.C001          -> เท่ากับ
        ?cust_id=in.(C001,C002)   -> อยู่ในชุด
    ฝั่ง server แกะด้วย RouteUtils.stripEq() และ parseInList()
  * endpoint ที่คืนของชิ้นเดียว ยังคืนเป็น JSON array ที่มีสมาชิกตัวเดียว
  * รองรับ header Prefer: return=representation และ resolution=merge-duplicates
  * POST /rpc/set_app_context เป็น stub ที่ไม่ทำอะไร มีไว้ให้ flow login เดิมไม่พัง

!! กับดักที่เคยทำให้หน้าสถิติพัง !!
  stripEq() รู้จักแค่ "eq." ไม่รู้จัก "in." route ที่รับแต่ id เดี่ยวแล้วเจอ
  "in.(A1,A2,...)" จะเอาสตริงทั้งก้อนไปค้นเป็น id เดียว แล้วตอบ 404 ทั้งที่ข้อมูล
  มีอยู่ครบ ต้องแกะด้วย parseInList() ก่อนเสมอ

endpoint รุ่นใหม่ที่ "ไม่" ใช้รูปแบบนี้ (เป็น REST ธรรมดา):
  /sync/v2/cursor, /sync/v2/changes, /sync/v2/snapshot/{entity}
  /customer/search, /customer/lookup
  /account/complete-initial-setup
  /places/autocomplete, /places/reverse

3.5 การกันคำขอซ้ำ (idempotency)
--------------------------------------------------------------------------------
endpoint ที่สร้างข้อมูลรับ header Idempotency-Key เป็น UUID แอปสร้างค่านี้ตอนสร้าง
แถวในเครื่องและเก็บไว้ในคอลัมน์ operation_id พอ retry ก็ส่งค่าเดิม

ฝั่ง server เก็บคู่ (key, hash ของ payload) ไว้
  * key เดิม payload เดิม  -> คืนผลเดิม ไม่สร้างซ้ำ
  * key เดิม payload ต่าง  -> 409 Conflict
นี่คือเหตุผลที่ยิงซ้ำตอนเน็ตกระพริบแล้วไม่ได้ข้อมูลซ้ำสองแถว

4.2 การอัปโหลด (outbox) ทำงานอย่างไร
--------------------------------------------------------------------------------
ตัวจริงคือ utils/SyncManager.doSync() ถูกเรียกจาก SyncWorker

การลงคิว (utils/SyncManager.scheduleSync):
  - OneTimeWorkRequest ชื่อเฉพาะ "DataSyncWorkName"
  - Constraints: NetworkType.CONNECTED
  - Backoff: EXPONENTIAL เริ่ม 10 วินาที
  - ExistingWorkPolicy.KEEP  <- สำคัญ: ถ้ามีงานรออยู่แล้วจะไม่สร้างใหม่ทับ
    เพราะ scheduleSync ถูกเรียกจาก 57 จุดทั่ว repository ถ้าใช้ REPLACE
    การบันทึกถี่ ๆ จะรีเซ็ตเวลา backoff ใหม่ทุกครั้งจนไม่เคยได้ส่งสักที

ลำดับการส่งใน doSync หนึ่งรอบ:
  1. เก็บกวาดไฟล์แนบที่ไม่มีใครอ้างถึงแล้ว
  2. POST /rpc/set_app_context (stub ไม่ทำอะไร แต่คงไว้ให้ flow เดิมครบ)
  3. ลูกค้า (lead) ที่ is_synced = 0
  4. ผู้ติดต่อ
  5. โครงการ
  6. นัดหมาย -> ตามด้วยผู้เข้าร่วมของนัดนั้น
  7. ผลการขาย -> ตามด้วยรูปและเช็คลิสต์
ลำดับนี้สำคัญ เพราะของทีหลังอ้างถึง id ของของก่อนหน้า

ข้อจำกัดต่อรอบ: MAX_ROWS_PER_ENTITY_PER_RUN = 100 แถวต่อชนิด ถ้าเหลือจะคืนผลเป็น
"ให้ลองใหม่" แล้ว WorkManager จะตามต่อด้วย backoff ไม่ใช่ทำทีเดียวจนหมดแล้ว timeout

การแปลง TEMP- id เป็น id จริง:
  แถวที่สร้างตอนออฟไลน์ได้ id ขึ้นต้นด้วย "TEMP-" ซึ่ง outbox ใช้ตัดสินว่าจะ POST
  (สร้างใหม่) หรือ PATCH (แก้ของเดิม) พอ POST สำเร็จและได้ id จริงกลับมา
  LocalIdMappingDao จะย้ายทุกการอ้างอิงไปที่ id ใหม่ในครั้งเดียว รวมถึงย้าย alarm
  ของนัดหมายไปอยู่ใต้ id ใหม่ด้วย (ไม่งั้นยกเลิกการเตือนไม่ได้อีกเลย)

4.3 การจัดการความล้มเหลว
--------------------------------------------------------------------------------
แยกเป็นสองพวกชัดเจน:

  ชั่วคราว (ลองใหม่ได้)   : ไม่มีเน็ต, timeout, 429, 5xx
      -> ไม่บันทึกอะไร ปล่อยให้ WorkManager retry ด้วย backoff

  ถาวร (ลองกี่ครั้งก็เหมือนเดิม) : 400, 403, 404, 409, 422
      -> บันทึกลงตาราง sync_rejection พร้อมรหัสและเหตุผล
      -> แถวนั้นจะถูก "ข้าม" ในรอบถัดไป ไม่วนยิงซ้ำไม่จบ
      -> แต่จะถูกลองใหม่ "หนึ่งครั้งต่อการเปิดแอปหนึ่งรอบ" เผื่อต้นเหตุถูกแก้แล้ว
         (เช่นแอดมินให้สิทธิ์เพิ่ม) ไม่งั้นข้อมูลจะค้างในเครื่องตลอดกาลแบบเงียบ ๆ

422 ถูกนับเป็นการปฏิเสธถาวรอยู่แล้ว ซึ่งเป็นเหตุผลที่กติกานัดหมายฝั่ง server เลือก
ตอบ 422 — แอปจะได้ไม่ retry วนและผู้ใช้ได้เห็นว่ามีอะไรไม่ผ่าน

ผลของทั้งรอบถูกสรุปเป็น SyncRunResult แล้ว SyncWorker ตัดสินว่า:
  มี LOCAL_FATAL หรือ auth ล้ม -> Result.failure()  (retry ไปก็วนเปล่า)
  มีอันที่ควรลองใหม่           -> Result.retry()
  นอกนั้น                      -> Result.success()

4.4 !! คำถามที่ถามบ่อย: ปิดแอปแล้วข้อมูลขึ้นเองไหม !!
--------------------------------------------------------------------------------
ขึ้นเอง ไม่ต้องเปิดแอปอีกรอบ

เหตุผล: WorkManager เก็บงานไว้ในฐานข้อมูลของตัวเอง ไม่ได้อยู่ในหน่วยความจำของแอป
  - ปัดแอปออกจาก recent apps  -> งานยังอยู่
  - รีบูตเครื่อง               -> งานยังอยู่ (WorkManager มี boot receiver ของตัวเอง)
  - พอเงื่อนไข CONNECTED เป็นจริง ระบบปฏิบัติการจะ "ปลุก process ของแอปขึ้นมา"
    เพื่อรัน worker โดยที่ผู้ใช้ไม่ต้องแตะอะไรเลย

ข้อยกเว้นที่ต้องรู้ และแก้ที่ฝั่งแอปไม่ได้:
  (ก) ถูก Force stop
      ถ้าผู้ใช้กด "บังคับหยุด" ในตั้งค่าระบบ หรือตัวจัดการแบตเตอรี่ของเครื่อง
      (Xiaomi, Oppo, Vivo, Realme, Huawei มีพฤติกรรมนี้) สั่งหยุดแอป
      Android จะ "ไม่ปลุก" แอปนั้นอีกเลยไม่ว่าทางใด จนกว่าผู้ใช้จะเปิดแอปเอง
      ไม่มีโค้ดใดเอาชนะข้อนี้ได้ ทางแก้คือบอกผู้ใช้ให้ตั้งแอปเป็น
      "ไม่จำกัดการใช้แบตเตอรี่" และปลดล็อก autostart
  (ข) Doze mode
      เครื่องวางนิ่งนาน ๆ งานอาจถูกเลื่อนไปทำในช่วง maintenance window
      คือช้าลง ไม่ใช่ไม่ทำ

ตาข่ายรองรับ: PeriodicDataSync รอบ 6 ชั่วโมง ลงทะเบียนแบบ KEEP ตอนเปิดแอป
(ใช้ KEEP ไม่ใช่ UPDATE เพราะถ้าเปิดแอปบ่อย ๆ แล้วรีเซ็ตรอบใหม่ทุกครั้ง
จะไม่มีวันครบรอบ) ตัวนี้ไม่ได้แก้เคส force stop แต่กู้เคสที่งานหลุดจากคิวด้วย
สาเหตุอื่น ทำให้ "ค้างยาวเงียบ ๆ" กลายเป็น "ช้าสุด 6 ชั่วโมง"

4.5 การดาวน์โหลด (delta sync v2)
--------------------------------------------------------------------------------
DownloadSyncWorker ทำสามขั้นตามลำดับ:

  ขั้นที่ 1 — Bootstrap (ทำครั้งแรก หรือเมื่อ cursor ใช้ไม่ได้แล้ว)
      ก. GET /sync/v2/cursor      จองตำแหน่งปัจจุบันไว้ก่อน
      ข. GET /sync/v2/snapshot/{entity} ทีละชนิด แบ่งหน้าแบบ keyset
         ชนิดที่ดึง: lead_customer, contact_person, project, appointment,
                     activity_result, appointment_contact
      ค. ทุกหน้าลงไปพักที่ตาราง sync_snapshot_item ก่อน
      ง. ครบแล้วค่อย swap เข้าตารางจริงใน transaction เดียว
      -> ระหว่างดาวน์โหลด ข้อมูลเดิมในเครื่องยังใช้งานได้ตามปกติ
      -> ถ้า process ตายกลางทาง สถานะยังเป็น IN_PROGRESS แล้วเริ่มใหม่ทั้งชุด
         ไม่ใช่เชื่อข้อมูลครึ่ง ๆ กลาง ๆ

  ขั้นที่ 2 — Delta
      GET /sync/v2/changes?after=<cursor>&limit=  วนจนกว่าจะหมด
      การเปลี่ยนแปลงที่เกิดระหว่างดาวน์โหลด snapshot จะมี seq > cursor
      จึงถูกเล่นซ้ำในขั้นนี้ ไม่มีช่องหาย

  ขั้นที่ 3 — Master data
      ดึงข้อมูลตั้งต้น (สถานะโครงการ เหตุผลที่ไม่ได้งาน ปัจจัยดีล) ซึ่งมีค่าสำรอง
      ฝังมากับ APK อยู่แล้ว จึงไม่ถือเป็นความล้มเหลวถ้าดึงไม่ได้

ฝั่ง server: change feed ไม่ได้เขียนโดยโค้ด Kotlin แต่เป็น trigger ในฐานข้อมูล
(migrations/add_sync_change_feed.sql) ที่เขียนลงตาราง sync_change "ใน transaction
เดียวกับการเขียนข้อมูลธุรกิจ" ถ้าเขียน feed ไม่สำเร็จ การเขียนข้อมูลก็ล้มตาม
จึงไม่มีทางมีข้อมูลที่ไม่ถูกบันทึกไว้ใน feed

!! กับดักที่เคยเจอ: แบนเนอร์ค้าง !!
  ธง _failedParts ถูกตั้งเมื่อ DownloadSyncWorker ล้ม และถูกล้างเมื่อ worker
  "ตัวเดียวกัน" รันสำเร็จเท่านั้น แต่ตอนเน็ตกลับมา สิ่งที่ถูกปลุกคือ worker
  ฝั่งอัปโหลด ข้อมูลจึงขึ้นได้ตามปกติแต่แบนเนอร์ค้างอยู่
  แก้แล้วโดย: พออัปโหลดสำเร็จ (= เน็ตใช้ได้แน่) และยังมี failed parts ค้าง
  HomeViewModel จะสั่งดาวน์โหลดซ้ำให้แบนเนอร์หายเอง

4.6 เวลาอ้างอิงจากเซิร์ฟเวอร์ (ServerTimeAnchor)
--------------------------------------------------------------------------------
ปัญหา: กติกานัดหมายตัดสินจาก "ตอนนี้กี่โมง" แต่ผู้ใช้แก้นาฬิกาเครื่องเองได้ และงาน
ที่ทำตอนออฟไลน์กว่าจะส่งถึง server อาจผ่านไปหลายชั่วโมง

วิธี:
  * ทุก HTTP response มี header Date จาก server อยู่แล้ว interceptor เก็บค่านั้น
    คู่กับ SystemClock.elapsedRealtime() ซึ่งเดินหน้าอย่างเดียวและผู้ใช้แก้ไม่ได้
    (ไม่ต้องเพิ่มฟิลด์ server_time ในทุก endpoint)
  * เวลาปัจจุบัน = เวลา server ที่จำไว้ + ส่วนต่างของ elapsedRealtime
  * ถือว่า "เชื่อไม่ได้" เมื่อ เครื่องรีบูต หรือ เวลาเครื่องถูกแก้
    ตรวจด้วยการเทียบ "เวลาบูตที่ประมาณได้" (wall clock ลบ uptime) ว่าขยับเกิน 5 วินาที
  * เชื่อไม่ได้ = บอกตามตรง ไม่ใช่แอบใช้เวลาเครื่องแล้วอ้างว่าเชื่อได้

ใช้ที่ไหน: ตอนผู้ใช้กดแก้แผนนัดหมาย แอปประทับเวลานี้ลงแถว (คอลัมน์ plan_edit_at
และ plan_edit_time_trusted) แล้วส่งขึ้นไปพร้อมคำขอเป็น client_modified_at
เพื่อให้ server ตัดสินกติกา ณ เวลาที่แก้จริง ไม่ใช่เวลาที่คำขอเดินทางมาถึง

    ที่ "ไม่" นับโดยตั้งใจ: check_in_* / plan_status / project_code / cust_code / note
    เพราะการเช็คอินเกิดหลังเวลาเริ่มนัดเสมอ ถ้านับรวมจะบล็อกการเช็คอินทั้งระบบ
  * ตรวจอยู่ใน transaction เดียวกับการเขียน บนแถวที่ SELECT ... FOR UPDATE ไว้
    กันคำขออีกใบขยับเวลานัดแทรกระหว่างอ่านกับเขียน
  * ปฏิเสธด้วย HTTP 422

งานที่ทำตอนออฟไลน์แล้วส่งช้า:
  ถ้าคำขอมี client_modified_at + client_time_trusted=true server จะตัดสินใหม่
  ณ เวลาที่อ้างว่าแก้ โดยมีด่านกันการโกหก: ต้องมาจาก anchor จริง, ต้องไม่อยู่อนาคต
  (เผื่อคลาด 5 นาที), ต้องไม่เก่ากว่าตอนที่นัดถูกสร้าง และสถานะปัจจุบันยังถูกตรวจ
  ตามปกติ จึงย้อนปลดล็อกนัดที่ completed ไปแล้วไม่ได้

ส่วนที่ 7 — การยืนยันตัวตนและสวิตช์ rollout

7.1 JWT และสองวงของการยืนยันตัวตน
--------------------------------------------------------------------------------
JWT เป็น HMAC256 issuer pp68-backend audience pp68-mobile อายุ 168 ชั่วโมง
claim ที่จำเป็นคือ user_id ซึ่ง route ใช้จำกัดขอบเขตข้อมูล ตัวตนคือแถว employee
ที่ emp_code = อีเมลแบบตัวพิมพ์เล็กตัดช่องว่าง รหัสผ่านเก็บเป็น BCrypt และมีทาง
เทียบแบบ plaintext สำรองไว้สำหรับแถวเก่าที่ยังไม่ถูกแปลง

claim เพิ่มเติมจาก Phase 4A: credential_version และ setup_only

  jwt-auth  (ใช้กับ API ธุรกิจทั้งหมด)
      ปฏิเสธ token ที่ credential_version ไม่ตรงกับแถว employee แล้ว
      ปฏิเสธ token ที่เป็น setup_only
      token เก่าที่ไม่มี claim พวกนี้เลย ยังผ่านในฐานะเวอร์ชัน 1 (แอปรุ่นเก่าใช้ได้)

  jwt-setup (ใช้กับ /account/complete-initial-setup เท่านั้น)
      รับเฉพาะ token ที่เป็น setup_only และเจ้าของยังมี password_change_required

ตั้งค่าบัญชีสำเร็จ = credential_version +1 ทำให้ token ทุกใบที่ออกก่อนหน้าใช้ไม่ได้ทันที

Rate limit: ทุก endpoint ที่รับรหัสผ่านอยู่ในบล็อกเดียวกัน 30 ครั้ง/นาที คิดตาม
ต้นทางคำขอที่อ่านจาก CF-Connecting-IP หรือ X-Forwarded-For
เหตุผลที่คิดตามต้นทางไม่ใช่ราย emp_code: การจำกัดราย emp_code เปิดให้ใครก็ได้ยิงใส่
บัญชีเป้าหมายจนเจ้าตัวเข้าไม่ได้ และภัยจริงคือการเดา emp_code กับรหัสเริ่มต้นร่วม

7.2 สวิตช์สองตัวที่ต้องเปิดด้วยมือ
--------------------------------------------------------------------------------
ทั้งสองตัว "ไม่" เปิดเองตอน deploy โดยตั้งใจ เพื่อให้ deploy backend ก่อนปล่อยแอปได้

  (1) APPOINTMENT_POLICY_V2 — บังคับกติกานัดหมายฝั่ง server
      ใส่เป็นบรรทัดในไฟล์ .env ที่รากโปรเจกต์บน server แล้ว restart
          echo 'APPOINTMENT_POLICY_V2=true' >> .env
          systemctl restart pp68-backend
      ยืนยันจาก log ตอน start:
          PP68 Backend started on port 8080 (appointment_policy_v2=true)
      ถ้าขึ้น false แปลว่าไฟล์ไม่ถูกอ่าน เกือบทุกครั้งคือ WorkingDirectory ของ
      systemd ไม่ได้ชี้มาที่รากโปรเจกต์
      ปิดกลับ: ลบบรรทัดนั้นแล้ว restart ไม่ต้อง rollback โค้ดหรือแตะฐานข้อมูล

  (2) password_change_required — บังคับตั้งรหัสผ่าน/เบอร์ครั้งแรก
      migration สร้างคอลัมน์เป็น FALSE ทุกบัญชี หน้าตั้งค่าจะไม่โผล่จนกว่าจะเปิดเอง
      ทดสอบทีละบัญชี:
          UPDATE employee SET password_change_required = TRUE
          WHERE emp_code = 'อีเมลตัวพิมพ์เล็ก';
      เปิดทั้งบริษัท: รัน migrations/oneoff_enable_required_account_setup.sql

  !! ห้ามเปิดสวิตช์ไหนก็ตามก่อนที่ APK รุ่นที่รองรับจะถึงมือผู้ใช้ครบ !!
     เปิด (1) ก่อน = แอปรุ่นเก่าแก้นัดหมายไม่ได้เลย ได้ 422 ทุกครั้ง
     เปิด (2) ก่อน = แอปรุ่นเก่า login ได้แต่ไม่มีหน้าให้ตั้งค่า ใช้งานไม่ได้ทั้งหมด

7.3 ฉบับร่างนัดหมายหลายรายการ (Phase 4C)
--------------------------------------------------------------------------------
ตาราง appointment_draft ใน Room เป็นข้อมูลในเครื่องล้วน ไม่เข้า change feed
ไม่มี is_synced และไม่มี @SerializedName สักฟิลด์ จึงไม่มีทางหลุดขึ้น server

  * เก็บได้สูงสุด 20 รายการต่อบัญชี เต็มแล้วปฏิเสธและพาไปหน้ารายการให้ผู้ใช้เลือกลบ
    ไม่ลบของเก่าสุดให้เอง การนับโควตาอยู่ใน transaction เดียวกับการเขียน
  * หมดอายุ 30 วัน ลบตอนเปิดหน้ารายการ ไม่มี worker แยก
  * ทุก query กรองด้วย owner_key (SHA-256 ของ user id) และ DAO ตั้งใจไม่มีเมธอด
    ที่คืนร่างของทุกบัญชี เพราะเครื่องถูกใช้ร่วมกันระหว่างพนักงานขาย
  * logout/สลับบัญชีจะลบร่างไปพร้อม clearAllTables() และผู้ใช้ได้เห็นจำนวนก่อนยืนยัน
  * ร่างยุคเก่าที่อยู่ใน SharedPreferences ถูกย้ายเข้า Room เฉพาะเมื่อพิสูจน์ได้ว่า
    เป็นของบัญชีที่ล็อกอินอยู่ พิสูจน์ไม่ได้ให้ลบทิ้ง
  * เปิดร่างแล้ว TEMP- id ที่ได้รหัสจริงไประหว่างนั้นจะถูกแปลงให้ ถ้าโครงการหรือ
    บริษัทที่อ้างถึงถูกลบไปแล้ว จะแสดงชื่อที่เก็บไว้ตอนบันทึกร่างและบังคับเลือกใหม่

ฟอร์มอื่นอีกสี่ตัว (ลูกค้า โครงการ ผู้ติดต่อ ผลการขาย) ยังใช้ร่างแบบรายการเดียวบน
SharedPreferences (utils/DraftStore) ตามเดิม

ก.3 อ่านอาการผิดปกติจากรหัสที่ได้
--------------------------------------------------------------------------------
  522           Cloudflare ต่อ origin ไม่ได้ — nginx หรือเครื่อง .225 ดับ
                หรือ LAN ออฟฟิศหลุด ไม่ใช่ความผิดของโค้ด backend
  502 / 504     nginx ถึง แต่ backend ที่ .177:8080 ไม่ตอบ (service ตาย/ค้าง)
  413           ไฟล์ใหญ่เกิน client_max_body_size ของ nginx
                (เคยเจอตอนอัปรูปจากกล้องจริง แก้แล้วด้วยการตั้ง 20M)
  401           token หมดอายุ/ไม่ถูกต้อง แอปจะล้าง token แล้วเด้งไปหน้า Login
                ยกเว้นบน login/register/change-password/setup ซึ่งแปลว่ารหัสผิด
  405 vs 404    405 = path มีอยู่แต่ผิด method  |  404 = ยังไม่มี path นั้น
                ใช้เทียบว่าโค้ดเวอร์ชันใหม่ขึ้น production หรือยังโดยไม่ต้องมี token
  410           GET /customer โดยเฉพาะ — ตั้งใจปิด ไม่ใช่ความผิดพลาด
  422           กติกาธุรกิจปฏิเสธ (ดูส่วนที่ 5) แอปนับเป็นการปฏิเสธถาวร

ค.2 pp68-backend.service
--------------------------------------------------------------------------------
  รันเป็น systemd service ตั้ง Restart=on-failure และ enabled ไว้แล้ว
  (รีสตาร์ทเองเมื่อ crash หรือเครื่องรีบูต)

    systemctl status pp68-backend --no-pager
    systemctl restart pp68-backend

  ห้าม kill process java ตรง ๆ และห้าม systemctl stop ทิ้งไว้ PID เปลี่ยนทุกครั้ง
  ที่ restart ให้ดูจาก systemctl status แทนการจำ PID

  !! WorkingDirectory สำคัญกว่าที่คิด !!
  Application.kt อ่านไฟล์ .env และ DatabaseFactory อ่านไฟล์ migrations/*.sql
  ด้วย path แบบ relative กับ working directory ของ process ถ้า unit ไม่ได้ชี้มาที่
  ราก repo จะเกิดสองอย่างพร้อมกันแบบเงียบ ๆ:
      - ทุก migration ถูกข้าม (มี warning บรรทัดเดียว)
      - ค่าใน .env ไม่ถูกอ่าน เช่น APPOINTMENT_POLICY_V2 จะเป็น false ตลอด
  ตรวจด้วย:  systemctl show pp68-backend -p WorkingDirectory

ค.3 nginx บน .225
--------------------------------------------------------------------------------
  config: /etc/nginx/sites-available/api-ploy.cskmitl.com

    nginx -t          ตรวจ syntax ก่อนเสมอ ห้าม reload ถ้า test ไม่ผ่าน
    nginx -s reload   ใช้คำสั่งนี้ตรง ๆ

  !! nginx บนเครื่องนี้ไม่ได้รันผ่าน systemd !!  systemctl reload nginx จะบอกว่า
  not active ซึ่งไม่ได้แปลว่า nginx ไม่ทำงาน

  ถ้า nginx ตัวนี้ล่ม แอปทั้งแอปคุยกับ server ไม่ได้เลย (ทุกคำขอ timeout หรือ
  connection refused ไม่ใช่แค่ error ฝั่ง backend) และผู้ใช้จะเห็นเป็น 522

  ค่า client_max_body_size 20M ถูกตั้งไว้ทั้ง block 80 และ 443 แล้ว ก่อนหน้านี้
  ไม่ได้ตั้งเลยจึงใช้ค่า default 1MB ทำให้รูปจากกล้องจริง (2-15MB) โดน 413 ทุกครั้ง

  บรรทัดที่ควรหาเวลาตรวจหลัง deploy:
    PP68 Backend started on port 8080 (appointment_policy_v2=...)
    migration ok: migrations/<ชื่อไฟล์>.sql
    migration FAILED: / migration SKIPPED (หาไฟล์ไม่เจอ...)
    login_failed emp_code=... reason=...          (audit การล็อกอินที่ล้มเหลว)
    appointment_policy action=... code=... enforced=...

ค.5 โปรเซสอื่นบนเครื่องเดียวกัน (ไม่ใช่ของระบบนี้)
--------------------------------------------------------------------------------
  port 3000  PostgREST ตัวเก่า — ยังเห็นรันอยู่บน .177 ไม่ทราบว่ามีใครใช้
  port 3001  URL เก่าที่แอปเคยเรียก (BASE_AUTH_URL เดิม) แอปย้ายมา 8080 หมดแล้ว
             แต่ไม่แน่ใจว่ามีระบบอื่นพึ่งอยู่ไหม
  docker containers เก่าอีกหลายตัว สถานะ Exited ทั้งหมด (ตอนนี้ deploy ผ่าน
  systemd โดยตรง ไม่ได้ใช้ docker แล้ว) ลบทิ้งได้แต่ไม่เร่งด่วน

  !! ถ้ามีเว็บอื่นที่ใช้ตาราง employee ร่วมกัน ให้รู้ไว้ว่าการบังคับตั้งรหัสผ่านใหม่
  จะเขียนทับคอลัมน์ password ด้วย BCrypt hash ใหม่ รหัสเดิมของผู้ใช้จะใช้กับเว็บนั้น
  ไม่ได้อีก และถ้าเว็บนั้นเทียบรหัสแบบ plaintext จะใช้ไม่ได้เลย

  path /uploads/** ซึ่งต้องมี JWT ถึงจะเปิดดูได้

ภาคผนวก จ — หน้าที่ของแต่ละฟังก์ชัน (ทุกโฟลเดอร์ ยกเว้น ui/)
================================================================================

ภาคผนวก ง บอกว่า "ไฟล์ไหนทำอะไร" ภาคผนวกนี้ลงลึกอีกชั้นว่า "ฟังก์ชันไหนทำอะไร"
ขอบเขตคือทุกโฟลเดอร์ของทั้งสองรีโป ยกเว้น ui/ ของฝั่งแอป (หน้าจอ ViewModel
คอมโพเนนต์ ธีม) ซึ่งเปลี่ยนบ่อยเกินกว่าจะคุ้มกับการเขียนระดับฟังก์ชัน

วิธีอ่าน
--------
- ชื่อฟังก์ชันเขียนแบบย่อ ตัดชนิดพารามิเตอร์ที่เดาได้ออก
- "★" = จุดที่เคยเป็นต้นเหตุบั๊กจริง หรือเป็นจุดที่แก้ผิดแล้วพังเงียบ
- ฟังก์ชันที่ชื่อบอกตัวเองชัดเจนอยู่แล้ว (getX/deleteX ตรงไปตรงมา) จะรวบเป็นกลุ่ม
  แทนการไล่ทีละบรรทัด เพื่อให้ของสำคัญไม่จมหาย

จ.1  แอป Android — data/model (37 ไฟล์)
================================================================================

ทั้งโฟลเดอร์เป็น data class ล้วน ไม่มีตรรกะ ไม่มีเมธอด ทำหน้าที่สองอย่างพร้อมกัน
ในคลาสเดียว คือเป็น Room entity (@Entity/@ColumnInfo) และเป็น DTO ของ JSON
(@SerializedName) จึงไม่มีอะไรให้อธิบายระดับฟังก์ชัน แต่มีกติกาที่ต้องรู้

★ กติกาที่พลาดแล้วพังเงียบ
  - ฟิลด์ที่ "ไม่มี" @SerializedName จะไม่ถูกส่งขึ้น server (ดู NetworkModule)
    การเติม @SerializedName ให้ฟิลด์ที่เป็นคอลัมน์เฉพาะเครื่อง เช่น isSynced,
    projectName, locationName จะทำให้มันเริ่มหลุดขึ้นไปทันทีโดยไม่มีอะไรเตือน
  - @ColumnInfo กับ @SerializedName ไม่จำเป็นต้องตรงกัน และไม่จำเป็นต้องตรงกับ
    ชื่อ property เช่นใน Project: createBy ผูกกับคอลัมน์ create_by ส่วน
    requestBy ผูกกับคอลัมน์ user_id — ห้ามเดาชื่อคอลัมน์จากชื่อ property
  - ข้อยกเว้นที่ตั้งใจ: SalesActivity.companyName มี @SerializedName("customer_name")
    เพื่อ "อ่าน" ชื่อบริษัทที่ server แนบมา แต่ไม่เคยถูกส่งกลับ เพราะทุกเส้นที่
    เขียนนัดหมายประกอบ Map เอง (CreateRequestPayloads / addActivityMap)

จัดกลุ่มตามการใช้งาน

  entity ที่เป็นทั้งตาราง Room และ DTO
    Customer, Project, SalesActivity (= นัดหมาย), ActivityResult,
    ActivityResultPhoto, ContactPerson, Branch, ActivityMaster,
    ActivityPlanItem, AppointmentContact, ProjectContact

  entity เฉพาะเครื่อง ไม่เคยขึ้น server
    AppointmentDraft      ฉบับร่างนัดหมาย มี owner_key (SHA-256) กันข้ามบัญชี
    AttachmentOutbox      คิวรูปที่ยังอัปโหลดไม่สำเร็จ
    LocalIdMapping        คู่ TEMP- id กับ id จริง
    SyncState             เคอร์เซอร์ + สถานะ bootstrap ของ delta sync
    SyncConflict          แถวที่ server กับเครื่องแก้ชนกัน
    SyncRejection         แถวที่ server ปฏิเสธถาวร
    SyncSnapshotItem      ตารางเงา ใช้ระหว่าง bootstrap ก่อน swap

  DTO อย่างเดียว (ไม่ใช่ตาราง)
    UserDto, AuthUser, LoginParams, RegisterApiRequest, ChangePassword,
    InitialAccountSetup, PlaceSuggestion, PlanItemDto, ChecklistInsertDto,
    CustomerLookup, ProjectFactorLog, SyncProtocol (SyncChangeEvent /
    SyncChangePage / SyncSnapshotPage / SyncCursorResponse)

  master data ที่มีคู่ Dto แยก (Dto = รูปจาก server, ตัวไม่มี Dto = รูปที่แอปใช้)
    ProjectStageMaster / ProjectStageMasterDto
    LossReasonMaster / LossReasonMasterDto
    DealFactorQuestion / DealFactorQuestionDto
    ActivityMaster / ActivityMasterDto
