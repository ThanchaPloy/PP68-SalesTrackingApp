## 1. ความเป็นมา

ระหว่างพัฒนา PP68 Sales Tracking (แอป Android + backend Kotlin/Ktor) ทีมพัฒนาได้ทำการเทียบ
โครงสร้างสิทธิ์การเข้าถึงข้อมูล (data access / ownership scoping) และกลไกจัดการสถานะ/ข้อมูลอ้างอิง
(master data, state transition) ของระบบ กับแนวทางที่ระบบ CRM เชิงพาณิชย์สองตัวที่เป็นที่ยอมรับ
ในอุตสาหกรรมใช้งานจริง คือ **Salesforce** (SaaS CRM เชิงพาณิชย์ชั้นนำ) และ **Odoo**
(ERP/CRM แบบโอเพนซอร์สที่มีโมดูล CRM ในตัว) เพื่อหาช่องว่าง (gap) ที่ระบบของตัวเองยังไม่ได้ทำ
ตามมาตรฐานทั่วไปของซอฟต์แวร์ประเภทเดียวกัน แล้วไล่ปิดช่องว่างเหล่านั้นเป็นชุดงาน W1 ถึง W6

## 2. แนวคิดเชิงมาตรฐานที่ใช้เป็นกรอบเทียบ (ความรู้ทั่วไปที่ตรวจสอบได้)

หัวข้อต่อไปนี้เป็นแนวคิดที่เป็นที่ยอมรับทั่วไปในระบบ CRM/ERP เชิงพาณิชย์ (ไม่เฉพาะ Salesforce/Odoo)
ใช้เป็นกรอบอ้างอิงทั่วไป ผู้เขียนวิจัยควรตรวจสอบและอ้างจากแหล่งต้นทางของแต่ละผลิตภัณฑ์เองอีกครั้ง:

- **Role-Based Access Control (RBAC) และ Record Ownership** — ระบบ CRM เชิงพาณิชย์ส่วนใหญ่
  (Salesforce ใช้ "Role Hierarchy" + "Sharing Rules"; Odoo ใช้ "Access Rights" + "Record Rules")
  กำหนดว่าผู้ใช้คนหนึ่งเห็นข้อมูลแถวใดได้บ้าง โดยอิงจาก "เจ้าของข้อมูล" (owner) และโครงสร้างทีม/สาขา
  ไม่ใช่ปล่อยให้ทุกคนเห็นทุกแถว
- **Audit Trail / Versioned History** — การเปลี่ยนสถานะของ record สำคัญ (เช่น Opportunity Stage
  ใน Salesforce, Lead Stage ใน Odoo) ควรถูกบันทึกเป็นประวัติที่ตรวจสอบย้อนหลังได้ ไม่ใช่เขียนทับค่าเดิม
- **Master Data Governance** — ค่าที่เป็นตัวเลือกคงที่ (เช่น stage, reason code) ควรมาจากตารางอ้างอิง
  กลางที่ดูแลจากส่วนกลาง ไม่ใช่ hard-code กระจายอยู่หลายที่ในโค้ด เพื่อให้แก้ไข/เพิ่มค่าใหม่ได้จุดเดียว
- **State Machine Integrity** — การเปลี่ยนสถานะของ record (เช่นโครงการ, นัดหมาย) ควรมีการ trigger
  ผลข้างเคียงที่ถูกต้องเสมอ (เช่น progress percentage ที่ผูกกับ stage) ไม่ใช่ปล่อยให้ค่าตกค้าง
  ไม่สอดคล้องกับสถานะจริง

## 3. หลักการออกแบบและแนวคิด Architecture ของระบบ PP68

ส่วนนี้ต่างจากหมวด 2 — หมวด 2 คือแนวคิดที่**ยืมมาจาก** Salesforce/Odoo ส่วนนี้คือสถาปัตยกรรม
**ของระบบ PP68 เอง** ที่ตรวจสอบได้ตรงจากโค้ดจริงในสองรีโป (`PP68SalesTrackingApp` และ `backend`)
ไม่ใช่การเดาหรือเรียบเรียงจากเอกสารที่หายไป เหมาะใช้เป็นตัวอย่างรูปแบบการออกแบบ (design pattern)
ในบทที่อธิบายการออกแบบระบบของรูปเล่มวิจัย ชื่อรูปแบบที่ใส่ไว้แต่ละข้อเป็นชื่อสากลที่ตรวจสอบ/อ้างอิง
เพิ่มได้จากหนังสือ/บทความวิชาการด้าน software architecture ทั่วไป

### 3.1 ฝั่งแอป Android

| แนวคิด / รูปแบบ | การนำไปใช้ในระบบ |
|---|---|
| **MVVM (Model–View–ViewModel)** | UI เขียนด้วย Jetpack Compose อ่าน-เขียนสถานะผ่าน `ViewModel` เท่านั้น ไม่เรียก repository ตรงจาก Composable |
| **Dependency Injection** | ใช้ Hilt ฉีด repository/service เข้า ViewModel แทนการสร้าง instance เองในคลาส ลดการผูกติดกัน (coupling) ระหว่างชั้น |
| **Repository Pattern** | แต่ละโดเมน (โครงการ, นัดหมาย, ผลการขาย ฯลฯ) มี Repository เป็นจุดเดียวที่ ViewModel คุยด้วย ซ่อนรายละเอียดว่าข้อมูลมาจาก Room หรือเครือข่าย |
| **Offline-First Architecture** | ทุก Repository อ่าน/เขียนที่ฐานข้อมูลโลคัล (Room) ก่อนเสมอ แล้วค่อยพยายามส่งขึ้นเซิร์ฟเวอร์ ถ้าออฟไลน์ข้อมูลในเครื่องยังเป็นความจริงหลัก (source of truth) ของผู้ใช้คนนั้น ไม่ใช่รอเครือข่ายก่อนถึงจะใช้งานได้ |
| **Outbox / Work Queue Pattern** | การบันทึกทุกครั้งจะเข้าคิวงาน (`WorkManager`) แยกจากการเขียนลง Room ทันที งานในคิวพยายามส่งขึ้นเซิร์ฟเวอร์เมื่อมีเครือข่ายโดยไม่ต้องให้ผู้ใช้เปิดแอปซ้ำ คล้ายรูปแบบ Transactional Outbox ในระบบกระจาย (distributed systems) ที่แยกการเขียนข้อมูลกับการส่งต่อออกจากกัน |
| **Idempotent Retry** | งานที่ส่งซ้ำ (เช่นเครือข่ายขาดช่วงที่กำลังส่ง) ใช้ idempotency key เพื่อให้เซิร์ฟเวอร์รู้ว่าเป็นการส่งซ้ำของคำขอเดิม ไม่สร้างข้อมูลซ้ำ |

### 3.2 ฝั่ง Backend

| แนวคิด / รูปแบบ | การนำไปใช้ในระบบ |
|---|---|
| **Layered Architecture** | แยกชั้นชัดเจน `routes` (รับ HTTP) → `usecase` (ตรรกะทางธุรกิจ เฉพาะโดเมนที่ซับซ้อน) → `repository` (คุยกับฐานข้อมูลผ่าน Exposed) → `database/tables` (นิยามตาราง) แต่ละชั้นรู้แค่ชั้นที่อยู่ติดกัน |
| **Dependency Injection** | ใช้ Koin ประกอบ (wire) repository/usecase เข้าด้วยกันที่จุดเดียว (`AppModule.kt`) ไม่กระจายการสร้าง instance ไปทั่วโค้ด |
| **Change Data Capture (CDC) ผ่าน Database Trigger** | การซิงค์ส่วนต่าง (delta sync) ไม่ได้ให้แอป poll ถามซ้ำๆ แต่ใช้ trigger ของฐานข้อมูลบันทึกทุกการเปลี่ยนแปลงลงตาราง feed กลาง (`sync_change`) ภายในทรานแซกชันเดียวกับการเขียนจริง แอปอ่านจาก feed นี้แทนการสแกนตารางหลักทั้งตาราง |
| **Keyset Pagination (Cursor-based)** | การซิงค์ครั้งแรก (initial snapshot) ใช้ cursor แบบ "แถวที่ id มากกว่าค่าก่อนหน้า" แทน `OFFSET` ปกติ เพื่อให้ page ข้างหน้าเสถียรแม้มีแถวใหม่แทรกเข้ามาระหว่างซิงค์ |
| **Append-Only Versioning (ไม่ใช่ Event Sourcing เต็มรูปแบบ แต่แนวคิดคล้ายกัน)** | ผลการขาย (`activity_result`) ไม่เขียนทับของเดิมเมื่อแก้ไข แต่เพิ่มแถวใหม่เป็นเวอร์ชันถัดไปของกลุ่มเดิม (`result_group_id`) เก็บประวัติทุกเวอร์ชันไว้ครบ ใช้ flag `is_latest` ชี้ว่าแถวไหนคือค่าปัจจุบัน |
| **Policy Object (แยกกฎธุรกิจจาก Transport Layer)** | กฎเรื่องเวลาที่แก้ไข/ลบ/บันทึกผลนัดหมายได้ ถูกแยกเป็นอ็อบเจกต์เดียว (`AppointmentPolicy`) ที่รับ `Clock` เป็นพารามิเตอร์ (dependency injection ของเวลา) ทำให้เทสต์ได้โดยไม่ต้องรอเวลาจริง และมีคู่แฝดฝั่งแอปที่ต้องให้ผลตรงกันเสมอ |
| **Feature Flag / Gradual Rollout** | กฎใหม่บางตัว (เช่นการบังคับกฎนัดหมายฝั่งเซิร์ฟเวอร์) เปิดผ่าน environment variable ปิดอยู่เป็นค่าตั้งต้น ทำให้ขึ้นระบบจริงได้โดยยังไม่เปลี่ยนพฤติกรรม รอให้ไคลเอนต์ทุกเครื่องอัปเดตก่อนจึงเปิดใช้งานจริง |
| **Natural Key vs. Surrogate Key** | `project.project_code` เป็นทั้งคีย์หลัก (primary key) ที่ตารางลูกอ้างอิง (FK) **และ** เป็นรหัสที่มีความหมายทางธุรกิจ (prefix บอกสาขา/ทีม) ในเวลาเดียวกัน — เป็น natural key ไม่ใช่ surrogate key (เช่น UUID แยกต่างหาก) ข้อเสียที่เจอจริง: รหัสนี้แก้ไขไม่ได้อย่างปลอดภัยหลังสร้าง (ตารางลูกอ้าง FK แบบ `ON DELETE CASCADE` แต่ไม่มี `ON UPDATE CASCADE` — เปลี่ยนค่าทีหลังจะ error หรือข้อมูลหลุด) บังคับให้ต้องรู้ค่าที่ถูกต้อง **ตั้งแต่ตอนสร้าง** ทั้งที่ทางธุรกิจบางครั้งยังไม่รู้จริง (เช่น "สาขาที่เปิดบิล" ของผู้จัดการภาคในระบบนี้) — ตัวอย่างคลาสสิกของเหตุผลที่ตำรา database design ส่วนใหญ่แนะนำให้ใช้ surrogate key แยกจากรหัสแสดงผล แต่การเปลี่ยนมาใช้ surrogate key ในระบบที่มีอยู่แล้วเป็นงาน migration ใหญ่ (ต้องแก้ทุกตารางที่อ้าง FK) จึงเลือกแก้ด้วยการบังคับกรอกข้อมูลให้ถูกตั้งแต่ต้นแทน |

### 3.3 หลักการร่วมที่เห็นได้ทั้งสองฝั่ง

- **Single Source of Truth ต่อโดเมน** — แต่ละประเภทข้อมูลมีจุดเดียวที่เป็นเจ้าของค่าจริง (เช่น
  ปัจจัยการขาย 4-9 ข้อเป็นของ "โครงการ" เจ้าของเดียว ไม่ใช่ของนัดหมายหรือผลการขายแต่ละครั้ง)
  ป้องกันข้อมูลชุดเดียวกันขัดแย้งกันเองในหลายที่
- **Fail-Safe ไม่ใช่ Fail-Silent** — เมื่อการเขียนขึ้นเซิร์ฟเวอร์ล้มเหลว ระบบไม่เงียบแล้วสูญหาย
  แต่เข้าคิวรอใหม่หรือแจ้งผู้ใช้ชัดเจน (ขึ้นกับว่าความล้มเหลวเป็นแบบชั่วคราวหรือถาวร)
- **Compatibility Layer เมื่อเปลี่ยนเทคโนโลยีกลางคัน** — backend เคยเป็น PostgREST มาก่อน แล้วเขียน
  ใหม่เป็น Ktor โดย**เลียนแบบรูปแบบการส่งข้อมูลเดิมของ PostgREST ไว้โดยตั้งใจ** เพื่อไม่ต้องแก้ไคลเอนต์
  ที่มีอยู่แล้วทั้งหมด เป็นตัวอย่างของการทำ compatibility/adapter layer ระหว่างการย้ายเทคโนโลยี backend
  แบบค่อยเป็นค่อยไป (endpoint ใหม่ที่เขียนหลังจากนั้นเลิกเลียนแบบรูปแบบเดิมแล้ว ใช้ REST ปกติ)

## 4. รายการช่องว่างที่พบและการแก้ไข (W1–W6)

สรุปจากบันทึกการทำงานจริง (ไม่ใช่เอกสารต้นฉบับ) — คอลัมน์ "มาตรฐานอ้างอิง" คือแนวคิดในหมวด 2
ที่การแก้ไขแต่ละข้อนำมาปรับใช้กับระบบนี้

| ลำดับ | ปัญหาที่พบในระบบ | มาตรฐานอ้างอิง | การแก้ไขที่ทำจริง |
|---|---|---|---|
| W1 | ช่องโหว่สิทธิ์การเข้าถึงข้อมูลข้ามสาขา/ข้ามเจ้าของในหลายตาราง (`customer`, `lead_customer`, `contact_person`, `appointment_checklist`, `appointment_contact`, `activity_result_photo`, `project_contact`, `project_stage_log`) และเชื่อค่าเจ้าของจาก request body แทนการบังคับจาก JWT | RBAC / Record Ownership | ใช้กลไก `CallerScope`/`resolveScope()` ที่มีอยู่แล้วบังคับทุกเส้นทาง GET/POST และบังคับอ่านเจ้าของจาก JWT เท่านั้น |
| W2 | คอลัมน์สถานะโครงการ (`project.project_status`) ไม่มีการตรวจสอบค่าเลย ทำให้มีค่าผิดปกติ ("ผี") หลุดเข้าประวัติสถานะถาวร | Master Data Governance | เพิ่ม CHECK constraint จำกัดค่าให้ตรงกับตัวเลือกจริงที่ UI ใช้ 9 ค่า พร้อมรวมจุดอ้างอิงตัวเลือกให้เหลือจุดเดียวในโค้ด (`ProjectStages.kt`) |
| W3 | Trigger คำนวณ progress percentage (`progress_pct`) ไม่ตอบสนองถูกต้องเมื่อสถานะเปลี่ยนเป็น Lost/Failed ทำให้ค่าตกค้างไม่ตรงกับสถานะจริง | State Machine Integrity | แก้ CASE ของ trigger ให้ครอบคลุมทุกค่าสถานะจริงที่แอปส่ง และ backfill ข้อมูลเก่าที่ค้างอยู่ |
| W4 | สนาม "เหตุผลที่ไม่ได้งาน" ปนกันระหว่างรหัสคงที่กับข้อความอิสระ ทำให้วิเคราะห์เชิงสถิติไม่ได้ | Master Data Governance | แยกเป็นสองคอลัมน์ (`loss_reason` = รหัส, `loss_reason_note` = ข้อความอิสระ) พร้อม migration ย้ายข้อมูลเก่า |
| W5 | ตัวเลือก stage/เหตุผล/ปัจจัยการขาย (deal factor) ยัง hard-code ในแอป ไม่ได้มาจากส่วนกลาง | Master Data Governance | ย้ายเป็นตารางอ้างอิงกลางฝั่ง backend พร้อม fetch-on-demand ฝั่งแอป (ไม่ cache ลง Room) |
| W6 | ชุดข้อกำหนดเฉพาะกิจจากการพูดคุยกับลูกค้า (ล็อกการแก้ไขนัดหมายใกล้วันนัด, สถานะ "ขาดนัด" ที่คำนวณสด ไม่เขียนลง DB, การผูกโครงการเข้ากับนัดหมายที่ยังไม่มีโครงการ ฯลฯ) | State Machine Integrity / Record Ownership | เพิ่ม helper กลาง (`AppointmentStatus.kt`) ให้ทุกหน้าจอ/ทุกรายงานอ่านสถานะที่ผ่านการคำนวณแล้วจุดเดียว ไม่ปล่อยให้แต่ละหน้าคำนวณเอง |

**สถานะการนำไปใช้จริง ณ วันที่บันทึก (28 ก.ย. 2569):** W1–W5 เสร็จสมบูรณ์และขึ้น production
(push ขึ้น `origin/main` ทั้งฝั่งแอปและ backend, ตรวจสอบกับฐานข้อมูลจริงแล้ว) W6 (รายการย่อย 7 ข้อ)
เสร็จสมบูรณ์และขึ้น production เช่นกัน

## 5. ข้อสังเกตเพิ่มเติมที่มีค่าในการเขียนวิจัย

ระหว่างทำ W1–W6 พบประเด็นที่น่าเป็นตัวอย่างสำหรับงานวิจัยเรื่องคุณภาพซอฟต์แวร์ได้ (ตรวจสอบได้จาก
ประวัติ git ของโปรเจกต์จริง ไม่ใช่การเดา):

- **โค้ดที่ compile ผ่านในเครื่อง ไม่ได้แปลว่า deploy ได้จริง** — พบไฟล์ที่จำเป็น 3 ไฟล์ไม่ได้ถูก
  commit เข้า git เลย (มีอยู่แค่ในเครื่อง dev) ทำให้ build บน server ล้มเหลวทั้งที่เครื่อง dev
  ผ่านตลอด เป็นตัวอย่างเรื่อง **configuration management** / **"works on my machine"**
- **Trigger ฐานข้อมูลบางตัวไม่ได้อยู่ใน migration file ที่ track ไว้** — มีอยู่ตรงๆในฐานข้อมูล
  จริงมาตั้งแต่ก่อนระบบ migration ถูกนำมาใช้ ทำให้ grep หาในโค้ดไม่เจอ เป็นตัวอย่างเรื่อง
  **schema drift** ระหว่างสิ่งที่ repo บันทึกไว้กับสภาพจริงของฐานข้อมูล
- **ตรรกะทางธุรกิจที่สำคัญ (ไม่ใช่แค่ validation) ซ่อนอยู่ใน DB trigger ที่ไม่มีใครเห็น** — การสร้าง
  รหัสโครงการ (ซึ่งผูกกับกฎทางธุรกิจเรื่องบทบาทพนักงาน) ทั้งหมดอยู่ใน trigger ที่ไม่ track เหมือน
  ตัวอย่างก่อนหน้า แต่คราวนี้คือ **ตรรกะที่ตัดสินใจรูปแบบข้อมูลจริง** ไม่ใช่แค่ constraint — ต้องขอ
  นิยามจริงจากผู้ดูแลฐานข้อมูลก่อนจะแก้ไขได้อย่างปลอดภัย เป็นตัวอย่างความเสี่ยงของการให้ "กฎทางธุรกิจ"
  อยู่ในชั้นที่ไม่มีเครื่องมือตรวจสอบ/ทดสอบอัตโนมัติรองรับ (ไม่มี version control, ไม่มี unit test)

## 6. แหล่งอ้างอิงที่ควรไปตรวจสอบเพิ่มก่อนใส่ในบทที่ 2 ของวิจัย

หัวข้อค้นหาที่แนะนำ (ไม่ใช่ลิงก์ที่ยืนยันแล้ว — ต้องเข้าไปตรวจสอบ URL/วันที่เข้าถึงเองก่อนอ้างอิง):

- เอกสารทางการของ Salesforce เรื่อง Role Hierarchy, Sharing Rules, และ Opportunity/Stage
  management (ค้นจาก Salesforce Help หรือ Trailhead โดยตรง)
- เอกสารทางการของ Odoo เรื่อง Access Rights, Record Rules, และโมดูล CRM (ค้นจาก Odoo
  Documentation โดยตรง)
- แนวคิด Role-Based Access Control (RBAC) — งานต้นแบบที่มักถูกอ้างถึงคือ Ferraiolo & Kuhn
  (ควรตรวจสอบปีพิมพ์/แหล่งพิมพ์จริงก่อนอ้าง)
- แนวคิด Audit Trail / Data Versioning ในระบบสารสนเทศเชิงธุรกิจ (ค้นคำว่า "audit trail pattern
  database design" หรือ "temporal data versioning" ในฐานข้อมูลงานวิจัย)
- **Offline-First Mobile Architecture** — ค้นคำว่า "offline-first architecture mobile application"
  หรือ "local-first software" (มีบทความ/เอกสารของทีม Ink & Switch ที่มักถูกอ้างถึงบ่อยในหัวข้อนี้
  ต้องตรวจสอบแหล่งพิมพ์จริงก่อนอ้าง)
- **Transactional Outbox Pattern** — ค้นคำว่า "transactional outbox pattern" ในบริบท microservices/
  distributed systems (เช่นเอกสารของ Chris Richardson, microservices.io)
- **Change Data Capture (CDC)** — ค้นคำว่า "change data capture database trigger" หรือเทียบกับ
  เครื่องมือเชิงพาณิชย์อย่าง Debezium เพื่ออ้างแนวคิดทั่วไป (ระบบนี้ไม่ได้ใช้ Debezium จริง ใช้ trigger
  ของ Postgres เขียนเอง แต่แนวคิดเป็นกลุ่มเดียวกัน)
- **Event Sourcing / Append-Only Data Model** — ค้นคำว่า "event sourcing pattern" หรือ "append-only
  database design" (Martin Fowler มีบทความอธิบายแนวคิดนี้ที่มักถูกอ้างถึง ต้องตรวจสอบ URL/วันที่
  เข้าถึงก่อนอ้าง)
- **Natural Key vs. Surrogate Key** — ค้นคำว่า "natural key vs surrogate key database design" (เป็น
  หัวข้อพื้นฐานในตำรา database design ทั่วไป เช่น "Database System Concepts" ของ Silberschatz et al.
  มักมีบทที่อธิบายหัวข้อนี้ ตรวจสอบรุ่น/เลขบทจริงก่อนอ้าง)
