# Prompt 14 — Mobile Phase 2 (6 รายการ) และรหัสโครงการตามบทบาทผู้สร้าง

เอกสารนี้คือคำสั่งพัฒนาเชิงลึกสำหรับเพิ่มความสามารถ 7 รายการให้ระบบที่สร้างจาก Prompt 00–13 แล้ว ต้องอ่าน Prompt 00–13 ก่อนเริ่ม โดยเฉพาะ 02 (auth/session), 04 (project pipeline), 05 (appointment), 06 (sales result versioning) เพราะหมวดนี้แก้ไขพฤติกรรมที่มีอยู่แล้ว ไม่ได้สร้างโมดูลใหม่ตั้งแต่ต้น

ทั้ง 7 รายการไม่ขึ้นกับกันโดยตรง ทำตามลำดับนี้เพื่อลดความเสี่ยง: รายการ 6 และ 3 ก่อน (ไม่พึ่งอะไรกันเลย) → รายการ 2 (ตัวเดียวที่ bump Room version) → รายการ 1 (backend ก่อน UI) → รายการ 7 → รายการ 4 (เปิดท้ายเสมอ เพราะกระทบ force-relogin ของผู้ใช้ทุกคนทันทีที่ปล่อย ต้องให้ของอื่นเสถียรก่อน) รายการ 5 เป็น audit ล้วน ทำเมื่อไรก็ได้

## 1. ผลลัพธ์ที่ต้องได้

- นัดหมายหนึ่งนัดผูกได้หลายโครงการ แต่ละโครงการมีประวัติผลการขายแยกเวอร์ชันของตัวเอง
- มีการเก็บ call log จากเครื่องแบบ write-only เข้า backend ผ่าน outbox เดิม
- โครงการที่เข้าสเตจ Quotation ต้องมีเดือนที่ต้องการสินค้า
- `versionCode` ขยับได้โดยไม่ทำให้งานออฟไลน์ที่ยังไม่ sync หายแบบไม่เตือน
- สแตกแผนที่/ค้นหาสถานที่ยืนยันแล้วว่าเป็น open source และมีแผนแก้ปัญหาค้นหาสถานที่จริงแยกจากประเด็น "เปลี่ยน map library"
- อายุ session ยาวขึ้นจาก 7 เป็น 30 วัน
- รหัสโครงการที่สร้างอัตโนมัติ ถูกต้องตามบทบาทผู้สร้างทุกกรณี รวมผู้จัดการภาคที่โครงการลงบิลคนละสาขากับสาขาตัวเอง

## 2. ขอบเขตและสิ่งที่ไม่ควรทำซ้ำ

ใช้ของเดิมจากหมวดก่อนหน้า:

- outbox, retry, idempotency จาก Prompt 07–08
- versioning ของ `activity_result` (`result_group_id`, `version`, `is_latest`) จาก Prompt 06
- draft mechanism แบบ Room ต่อบัญชีจาก Prompt 10 (ใช้แพทเทิร์นเดียวกันสำหรับ draft ใหม่ ไม่สร้างกลไก draft คู่ที่สาม)
- `AuthUser.role` ที่มาจาก `employee.empPost` ตอน login อยู่แล้ว (Prompt 02) — ห้ามเพิ่ม field หรือ API call ใหม่เพื่อรู้บทบาทผู้ใช้ ถ้า field เดิมพอ

ห้ามทำ:

- ห้ามเดา endpoint, field หรือ trigger ที่ยังไม่เห็นนิยามจริง (ดูหัวข้อ baseline audit) — โดยเฉพาะทุกอย่างที่เกี่ยวกับ `project_code`
- ห้าม fallback เงียบ ๆ เมื่อข้อมูลที่ควรบังคับกรอกไม่มีค่า ถ้าค่านั้นถูกใช้วิเคราะห์ข้อมูลภายหลังด้วย (ดูหัวข้อ 8)
- ห้ามสร้าง logic ย้าย/re-key primary key ของ `project` ด้วย `AFTER` trigger ที่พึ่ง `RETURNING` คืนค่าให้ caller — Postgres จับค่า `RETURNING` ก่อน `AFTER` trigger รันเสร็จ ค่าที่คืนจะเป็นแถวที่ธุรกรรมเดียวกันลบทิ้งไปแล้ว ถ้าจำเป็นต้อง re-key ให้ทำใน Kotlin application code เท่านั้น ไม่ใช่ trigger
- ห้าม restore ฟีเจอร์ที่ถูกลบไปแล้ว (call log) แบบ copy-paste โค้ดเก่าทั้งก้อน ให้ตรวจของเก่าเฉพาะส่วนที่ยังถูกต้อง แล้วเขียนโครงสร้างใหม่ให้เข้ากับ outbox/versioning ปัจจุบัน
- ห้ามเปิด server-side enforcement ของเดือนที่ต้องการสินค้าในรอบนี้
- ห้ามใช้ `fallbackToDestructiveMigration` หรือ migration ที่ล้างตารางเพื่อให้ build ผ่าน
- ห้ามถือว่า compile ผ่านเท่ากับ deploy ได้ — รายการ 2 และ 7 ต้อง verify กับฐานข้อมูล/อุปกรณ์จริงก่อน production

## 3. Baseline audit ก่อนแก้ไข

ก่อนเขียนโค้ด ให้สำรวจและรายงาน:

- `TokenManager.checkAppVersionAndForceRelogin()`, `clearToken()` และ `AuthRepository.login()` ทั้ง `isSameUser`/`hasProtectedLocalData`/`AccountSwitchBlockedException` — ต้องเข้าใจ chain นี้ให้ครบก่อนแตะ `versionCode` (รายการ 4)
- `ActivityResultDao`/`ActivityRepository` และกฎ versioning ปัจจุบันของ `activity_result` ว่าคีย์ด้วยอะไรอยู่แล้ว ก่อนเพิ่มมิติ "หลายโครงการ" (รายการ 1)
- โค้ด call log เดิมที่ถูกลบไปแล้ว (ถ้ายังหาใน git history ได้) — อ่านเฉพาะเพื่อดูว่าส่วนไหนยังถูกต้อง (เช่น การกรองเบอร์ตาม contact ที่มีอยู่) ไม่ใช่เพื่อ copy กลับ
- `Project.desiredCompletionDate`/`project.desired_completion_date` และทุกจุดที่เขียนคอลัมน์นี้ (ฝั่ง client เขียนตรง, ฝั่ง outbox replay, ฝั่ง backend `update()`) — ต้องพากันครบทั้งสามจุด (รายการ 3)
- `application.conf`'s `jwt.expireHours` ค่าปัจจุบัน (รายการ 6)
- สแตกแผนที่/place-search ปัจจุบันจริง ๆ (renderer, tile source, endpoint ค้นหาสถานที่) ก่อนสรุปว่าต้องเปลี่ยนอะไร (รายการ 5)
- **นิยามจริงของ trigger ที่สร้าง `project_code`** — ถ้าไม่มีอยู่ใน migration ที่ track เลย (สัญญาณเดียวกับ CHECK constraint PostgREST-era ที่ไม่อยู่ใน repo) ต้อง pull นิยามจริงจากฐานข้อมูล (เช่นผ่าน DBeaver/`pg_proc`) มาก่อนเขียน migration ใด ๆ ที่แก้ trigger นี้ ห้ามเขียนจากการเดารูปแบบ prefix (รายการ 7)
- คอลัมน์ที่แยกบทบาท "ผู้จัดการภาค" กับ "ผู้จัดการสาขาขาย" ได้จริง — ถ้าทั้งสองใช้ `emp_type` เดียวกัน ต้องตรวจว่า free-text field ใด (เช่น `emp_post`) แยกสองบทบาทนี้ได้แน่นอน ก่อนเขียนเงื่อนไขอิง field นั้น

ถ้าพบความขัดแย้งระหว่าง field/trigger จริงกับสมมติฐานในเอกสารนี้ ให้หยุดและรายงาน ไม่เดาต่อ

## 4. รายการ 1 — หนึ่งนัดหมายผูกได้หลายโครงการ

### กฎ

- นัดหมายมีโครงการหลัก (field เดิมที่ผูกอยู่) และผูกโครงการเสริมเพิ่มได้จากหน้าบันทึกผล ผ่านช่องทางเพิ่มโครงการแบบ bottom sheet
- คีย์ผลการขาย (`activity_result`) ด้วย **(appointment_id, project_code)** ไม่ใช่ appointment_id เดี่ยว ๆ — แต่ละโครงการ (หลักและเสริม) มีสาย version ของตัวเองตามกฎ append-only versioning เดิม
- เปิดนัดหมายที่เคยบันทึกผลหลายโครงการไปแล้วต้องโหลดกลับมาครบทุกโครงการ ไม่ใช่แค่โครงการหลัก — เขียน query/endpoint แบบคืน list ของผลทุกโครงการในนัดเดียว ไม่ผูกกับ query ประวัติโครงการเดี่ยวเดิม
- บันทึกเฉพาะโครงการเสริมที่กรอกข้อมูลครบ โดยไม่บล็อกการบันทึกโครงการหลักที่กรอกครบแล้ว (partial save ต้องทำได้)
- มี draft ของฟอร์ม "เพิ่มโครงการ" กู้คืนได้ตามกติกา draft เดิมของแอป

### จุดที่ต้องระวังเป็นพิเศษ

- Dropdown โครงการที่เลือกได้ในหน้า "เพิ่มโครงการ" ต้องโหลดได้ไม่ว่านัดหมายจะมีโครงการหลักผูกอยู่แล้วหรือไม่ — ห้ามเขียน condition ที่โหลดเฉพาะกรณี "ยังไม่มีโครงการผูก" เพราะเคสปกติที่สุดคือมีโครงการหลักผูกอยู่แล้ว
- partial save ทำให้หน้าจอเปิดทิ้งไว้แล้ว save ซ้ำได้เป็นครั้งแรก (ก่อนหน้านี้บันทึกครั้งเดียวจบเสมอ) — หลัง partial save ที่ไม่ปิดหน้า ต้อง refresh `resultId`/state ของโครงการที่บันทึกไปแล้วทันที ไม่งั้นการ save ครั้งที่สองจะส่ง id เปล่าไปสร้างสาย version ใหม่แยกกลุ่มโดยไม่ตั้งใจ
- ตรวจก่อนว่า entity ปัจจุบันเก็บ `project_code` ต่อแถวได้พอหรือไม่ ก่อนตัดสินใจเพิ่ม Room migration ใหม่ — ถ้า schema เดิมพอ ไม่ต้อง bump version

### Acceptance tests

- สร้างผลของโครงการเสริมแล้วเปิดนัดซ้ำ ต้องเห็นประวัติทั้งโครงการหลักและเสริมแยกกัน
- กรอกโครงการหลักครบ โครงการเสริมไม่ครบ แล้ว save ต้องได้ผลโครงการหลักบันทึกสำเร็จ โครงการเสริมไม่ถูกบันทึกแต่ไม่ error
- save โครงการหลักสำเร็จ เปิดฟอร์มทิ้งไว้ แก้แล้ว save ซ้ำ ต้องได้ version ที่ 2 ของกลุ่มเดิม ไม่ใช่กลุ่มใหม่

## 5. รายการ 2 — Call log จากเครื่อง (write-only)

### กฎ

- อ่านประวัติการโทรจาก `CallLog` ของเครื่อง ผ่าน runtime permission `READ_CALL_LOG`
- กรองเหลือเฉพาะเบอร์ที่ตรงกับ contact ที่มีอยู่ในระบบ ก่อนเก็บลง local DB — ห้ามเก็บประวัติการโทรทั้งหมดของเครื่องแบบไม่กรอง
- เก็บลง Room entity ใหม่ เข้า outbox เดิม (ไม่สร้าง upload path แยก) ให้ได้ retry/idempotency โดยอัตโนมัติ ใช้ flag `isSynced` ต่อแถว ไม่ใช้ watermark timestamp แบบ global
- แยก logic การ match/dedup เบอร์โทรออกจากชั้นที่อ่าน `ContentResolver` เพื่อ unit test ได้โดยไม่ต้องพึ่ง instrumentation/Robolectric
- **ขอบเขตรอบนี้คือ write-only** — ไม่สร้าง GET endpoint ไม่สร้าง UI อ่านกลับ แจกจ่ายเป็น internal APK เท่านั้น เพราะยังไม่ประกาศเหตุผลการใช้ `READ_CALL_LOG` สำหรับ Play Store
- คอลัมน์ฝั่ง client/server ต้องตั้งชื่อให้ตรงกันตั้งแต่ตอนออกแบบตาราง (`emp_code`/`cust_code` แบบเดียวกับ entity อื่นของระบบ) ห้ามปล่อยให้ชื่อเพี้ยนระหว่างสองฝั่ง

### ห้ามทำ

- ห้าม copy โค้ดเก่าที่เคยถูกลบกลับมาทั้งก้อน — ต้องออกแบบใหม่ให้เข้ากับ outbox/versioning ปัจจุบัน
- ห้ามขยายขนาดคอลัมน์ id เกินความจำเป็นโดยไม่ตรวจก่อนว่ารูปแบบ id จริงที่จะใช้ยาวแค่ไหน
- ห้ามรัน migration ที่สร้างตารางนี้กับฐานข้อมูล production โดยไม่ตรวจก่อนว่ามีตารางชื่อเดียวกันหลงเหลือจากฟีเจอร์เดิมที่ไม่เคย track ใน migration หรือไม่ — ถ้ามีและคอลัมน์ไม่ตรง ต้องจัดการตารางเก่าก่อน migration ใหม่จะรันทับไม่ถูก (migration ที่ปลอดภัยที่สุดคือ `CREATE TABLE IF NOT EXISTS` ซึ่งจะไม่แก้ตารางเก่าที่ผิดให้)

### Acceptance tests

- ปฏิเสธ permission แล้วฟีเจอร์ไม่ crash ไม่เก็บข้อมูลอะไร
- มีเบอร์ไม่ตรง contact ใดเลย ต้องไม่ถูกเก็บ
- ตัดเน็ตระหว่างเก็บ แล้วต่อเน็ตใหม่ ต้อง sync ได้โดยไม่ซ้ำแถว (idempotent)
- Room migration test (เทียบ schema export) ต้องผ่านบนอุปกรณ์/emulator จริงก่อนถือว่าเสร็จ ไม่ใช่แค่เขียน test ไว้

## 6. รายการ 3 — เดือนที่ต้องการสินค้า บังคับที่สเตจ Quotation

### กฎ

- "เดือนที่ต้องการสินค้า" ใช้ field เดิมที่เก็บวันที่ของโครงการ เก็บเป็นวันที่ 1 ของเดือนที่เลือก — ห้ามสร้างคอลัมน์ใหม่
- บังคับกรอกเฉพาะตอนโครงการ**เข้าสู่สเตจ** Quotation เป็นครั้งแรกเท่านั้น — โครงการที่อยู่ Quotation มาก่อนกฎนี้และไม่มีค่า ห้ามบล็อกการแก้ไขอื่น ให้แสดง banner เตือนแทน
- จุดเขียนค่านี้ต้องครบทั้งสามทาง: เขียนตรงจากหน้าแก้ไขโครงการ, replay จาก outbox สำหรับงานที่ทำออฟไลน์, และ endpoint แก้ไขโครงการฝั่ง backend — ถ้าพากันแค่บางทางจะมีช่องที่ค่าหลุดได้
- Logic การแปลง/ตรวจรูปแบบเดือนอยู่ที่เดียว ไม่กระจาย validation ไปหลายหน้า

### ห้ามทำ

- ห้ามเปิด server-side enforcement ของ field นี้พร้อมกับรอบนี้ — ถ้าไคลเอนต์รุ่นเก่ายังไม่มี field นี้ จะเซฟ Quotation ไม่ได้เลยทุกเคส ให้เปิดได้เฉพาะหลัง build ที่มี field นี้ถูกปล่อยใช้งานจริงแล้ว

### Acceptance tests

- สร้างโครงการใหม่แล้วเปลี่ยนสเตจเป็น Quotation โดยไม่กรอกเดือน ต้องถูกบล็อก
- โครงการเก่าที่อยู่ Quotation อยู่แล้วไม่มีเดือน ต้องแก้ไขฟิลด์อื่นได้ปกติ พร้อม banner เตือน
- แก้เดือนนี้ตอนออฟไลน์แล้ว sync ย้อนหลัง ค่าต้องขึ้น backend ถูกต้อง

## 7. รายการ 4 — Bump versionCode

### กฎ

ก่อนขยับ `versionCode`/`versionName` ต้องตรวจและยืนยันครบทุกข้อต่อไปนี้จากโค้ดจริง ไม่ใช่จากเอกสารเก่า:

1. กลไกตรวจเวอร์ชันตอนเปิดแอปเรียก clear เฉพาะ token/session ไม่ใช่ลบข้อมูลทั้งหมดทันที
2. รอบ login ถัดไปต้องมีการตรวจว่าเป็นผู้ใช้คนเดิมหรือไม่ โดยอ้างอิงจากข้อมูลที่ยังไม่ถูกล้าง (หรือยอมรับผลเป็น unknown ถ้าถูกล้างไปแล้ว)
3. ถ้ามีงานออฟไลน์ที่ยังไม่ sync ค้างอยู่ และผลตรวจคือ "อาจเป็นคนละคน" ต้อง**บล็อกและถามผู้ใช้ก่อน**ลบข้อมูลใด ๆ (ขึ้น UI ที่ผู้ใช้เลือกได้ว่าจะลบหรือยกเลิก) ห้ามลบเงียบ ๆ โดยไม่ขอความยืนยัน
4. ถ้าไม่มีงานค้าง ต้อง login ผ่านได้ตามปกติ ไม่ลบข้อมูลที่ไม่จำเป็นต้องลบ
5. ถ้า 3 หรือ 4 ไม่เป็นจริงในโค้ดปัจจุบัน ต้องแก้ safety chain นี้ให้ครบก่อน แล้วจึงขยับเลข

เขียนคอมเมนต์เตือนข้าง `versionCode` ให้ตรงกับพฤติกรรมจริงของ safety chain ณ ตอนนั้นเสมอ — ถ้าคอมเมนต์เดิมบอกว่าจะลบข้อมูลแบบไม่มีเงื่อนไข แต่โค้ดจริงมีด่านกันแล้ว ต้องแก้คอมเมนต์ให้ตรง ไม่ปล่อยให้คอมเมนต์หลอกคนในอนาคตว่าการ bump อันตรายกว่าที่เป็นจริง

### ห้ามทำ

- ห้าม bump เลขนี้ก่อนตรวจ chain ข้างต้นครบ
- ห้ามแก้ chain ให้ "ง่ายขึ้น" ด้วยการตัดการขอความยืนยันออกเพื่อให้ flow สั้นลง

### Acceptance tests

- มีงานค้าง (pending/rejected/conflict อย่างใดอย่างหนึ่ง) แล้ว bump เวอร์ชันจำลองการเปิดแอปรุ่นใหม่ครั้งแรก → login ต้องถูกบล็อกพร้อมตัวเลือกยืนยัน/ยกเลิก ไม่ใช่ error ทั่วไปหรือลบเงียบ
- ไม่มีงานค้าง แล้วทำแบบเดียวกัน → login ผ่านปกติ ไม่มีการลบ local data ที่ไม่จำเป็น

## 8. รายการ 5 — Map/location stack เป็น open source

### กฎ

- ตรวจสแตกปัจจุบันจริงก่อนเสนอเปลี่ยนแปลงใด ๆ ถ้า renderer และแหล่ง tile ที่ใช้อยู่เป็น open source อยู่แล้ว ให้ถือว่ารายการนี้ปิดได้โดยไม่ต้องแก้โค้ด renderer
- แยกประเด็น "map library" กับ "ค้นหาสถานที่" ออกจากกันเสมอ — ถ้าข้อร้องเรียนจริงคือหาสถานที่ไม่เจอ ให้ตรวจที่ endpoint ค้นหาสถานที่ (geocoding/places API) ก่อนเสนอเปลี่ยน map library ใด ๆ เพราะสองเรื่องนี้แก้คนละจุด
- ก่อนเสนอ library ใหม่ ให้ตรวจว่า library นั้นทำงานแบบ native บนแพลตฟอร์มเป้าหมายจริง หรือเป็นแค่ wrapper รอบ JS/WebView — wrapper มักแย่กว่าของเดิมทั้งความเร็วและ vector-tile support อย่าเสนอโดยไม่เช็ค
- ถ้า root cause คือ endpoint ค้นหาเป็น address-geocoding ไม่ใช่ POI search ให้เสนอเปลี่ยนไปใช้ endpoint ประเภท places/POI ของ provider เดิมก่อน (ค่าใช้จ่าย/ความเสี่ยงต่ำสุด) แล้วค่อยพิจารณาการถอดรหัส location code แบบ offline (เช่น Plus Code) เป็นชั้นเสริม ก่อนพิจารณา self-host ฐานข้อมูลสถานที่ใหม่ทั้งชุด

## 9. รายการ 6 — ขยายอายุ session 7 → 30 วัน

### กฎ

- เปลี่ยนค่า config อายุ JWT จาก 168 ชั่วโมง เป็น 720 ชั่วโมง เท่านั้น ไม่แก้ logic การออก/ตรวจ token
- อัปเดตเอกสารข้อกำหนด non-functional ที่อ้างค่าอายุ session เดิมให้ตรงกับค่าใหม่ ไม่ปล่อยให้เอกสารขัดกับ config จริง

### Acceptance tests

- token ที่ออกใหม่หลังแก้ ต้องมีอายุ 30 วันจริงเมื่อ decode
- token ที่ออกก่อนแก้ (อายุ 7 วัน) ยังใช้งานได้ตามอายุเดิมของมัน ไม่ถูกเพิกถอนก่อนเวลาเพราะเปลี่ยน config

## 10. รายการ 7 — รหัสโครงการตามบทบาทผู้สร้าง

### กฎ (ต้องได้ผลลัพธ์นี้เท่านั้น)

1. **ทีมโครงการ** — prefix คงที่ของทีมโครงการ ไม่ขึ้นกับสาขาใด ๆ
2. **ผู้จัดการสาขาขาย** — prefix = สาขาของผู้สร้างเอง
3. **ผู้จัดการภาค/โซน** — prefix = สาขาที่โครงการ**เปิดบิล** (ฟิลด์ billing branch) ไม่ใช่สาขาของผู้สร้าง **และต้องเลือกฟิลด์นี้บังคับตอนสร้างโครงการ** ไม่มี fallback ไปใช้สาขาตัวเองสำหรับบทบาทนี้

### เหตุผลเชิงกฎที่ต้องยึดเวลาออกแบบ (ห้ามข้าม แม้จะดูเหมือนทำให้เร็วขึ้น)

- รหัสโครงการไม่ใช่ label ตกแต่ง — ระบบวิเคราะห์ข้อมูลภายหลัง parse ข้อความ prefix ของรหัสโครงการตรง ๆ ไม่ได้อ่านจากคอลัมน์ billing branch แยก ดังนั้น prefix ผิดคือบั๊กข้อมูลจริง **ห้ามเสนอ fallback แบบ "ถ้าไม่รู้ billing branch ให้ใช้สาขาตัวเองไปก่อนแล้วแก้ทีหลัง"** เพราะสร้างข้อมูลผิดที่ต้องตามไล่แก้ย้อนหลังเสมอ
- ห้ามแก้ปัญหานี้ด้วยการ "แก้รหัสย้อนหลังอัตโนมัติผ่าน `AFTER` trigger เมื่อรู้ billing branch ทีหลัง" — Postgres ส่งค่าทาง `RETURNING` ก่อน `AFTER` trigger รันเสร็จ caller จะได้รหัสที่ธุรกรรมเดียวกันลบทิ้งไปแล้ว ถ้าจะทำ re-key ต้องทำในชั้น application code (Kotlin) ไม่ใช่ trigger และต้องรู้ child table ทั้งหมดที่อ้างรหัสนี้ก่อนเริ่ม — ทางนี้ซับซ้อนและเสี่ยงกว่าทางเลือกที่ 3 ด้านล่างมาก ให้ประเมินก่อนลงมือว่าคุ้มจริงหรือไม่
- ทางที่ถูกต้องและง่ายที่สุดคือบังคับกรอก billing branch ตอนสร้างโครงการสำหรับบทบาทนี้โดยตรง ตัดปัญหา "ต้องรู้ทีหลัง" ออกไปทั้งหมด

### สิ่งที่ต้องทำจริง

- **Backend:** ดึงนิยามจริงของ trigger ที่สร้างรหัสโครงการ (ดู baseline audit หัวข้อ 3) มาเขียนเป็น migration ที่ track ใน git ครั้งแรก (ต้อง byte-identical กับของจริง ยกเว้นกิ่งที่เพิ่มสำหรับผู้จัดการภาค) — ห้ามเขียน trigger ใหม่จากศูนย์โดยเดารูปแบบเดิม
- **Backend defense-in-depth:** endpoint สร้างโครงการต้องตรวจเองด้วยว่า ถ้าผู้สร้างเป็นผู้จัดการภาคและไม่ส่ง billing branch มา ให้ตอบ `400` พร้อมเหตุผลที่อ่านออก ไม่ปล่อยให้ trigger เป็นด่านเดียวที่ป้องกัน
- **App:** เช็คบทบาทผู้ใช้จาก field ที่มีอยู่แล้วจาก login response (ไม่เพิ่ม field/endpoint ใหม่) แล้วบังคับฟิลด์ billing branch เป็น required เฉพาะบทบาทผู้จัดการภาคในฟอร์มสร้างโครงการ ทั้งที่ตัว field (ดาว required) และใน validation ก่อน submit

### ห้ามทำ

- ห้ามเขียนเงื่อนไขแยกบทบาทโดยอิงชื่อ field ที่ยังไม่ตรวจว่าแยกสองบทบาทได้จริง (ดู baseline audit)
- ห้ามเปลี่ยนกฎของทีมโครงการหรือผู้จัดการสาขาขาย — ทั้งสองบทบาทนี้ถูกต้องอยู่แล้ว แก้เฉพาะกิ่งของผู้จัดการภาค

### Acceptance tests

- ผู้จัดการภาคสร้างโครงการโดยไม่กรอก billing branch → backend ปฏิเสธ ไม่สร้างแถว ไม่สร้างรหัสผิด
- ผู้จัดการภาคสร้างโครงการพร้อม billing branch → รหัสโครงการใช้ prefix ของสาขานั้น ไม่ใช่สาขาตัวเอง
- ผู้จัดการสาขาขายและทีมโครงการสร้างโครงการตามปกติ → ได้ผลลัพธ์เหมือนก่อนแก้ทุกกรณี (regression)
- ต้องรันเทียบกับฐานข้อมูลจริงหรือ staging อย่างน้อยหนึ่งรอบ ก่อนถือว่ารายการนี้พร้อม production — unit test ระดับ JVM ที่ไม่มี Postgres จริงไม่พอ

## 11. ลำดับการพัฒนาที่แนะนำ

1. รายการ 6 และ 3 (ไม่พึ่งกัน ทำคู่กันได้)
2. รายการ 2 — เพราะเป็นตัวเดียวที่ bump Room version ถ้าจะรวม migration หลายตัวในรอบเดียวกันให้รวมที่จุดนี้
3. รายการ 1 — backend (คีย์ผลตาม appointment+project, endpoint คืน list) ก่อน UI (bottom sheet, draft, partial save)
4. รายการ 7 — ดึงนิยาม trigger จริงก่อนเขียน migration ใด ๆ
5. รายการ 4 — ปิดท้ายเสมอ หลัง 1/2/3/6/7 เสถียรและผ่าน test แล้ว
6. รายการ 5 — ทำเมื่อไรก็ได้ เป็น audit + แผน ไม่บังคับต้องมีโค้ดเปลี่ยนในรอบนี้

## 12. Definition of Done

งานจะถือว่าเสร็จเมื่อ:

- ทั้ง 6 รายการ (ยกเว้นรายการ 5 ที่เป็น audit) compile และ unit test ผ่านทั้ง Android และ backend
- รายการ 1 ผ่าน acceptance tests ในหัวข้อ 4 ครบ รวมสองจุดที่ต้องระวังเป็นพิเศษ
- รายการ 2 ผ่าน Room migration test บนอุปกรณ์/emulator จริง และยืนยันแล้วว่าไม่มีตารางชื่อซ้ำที่ผิด schema หลงเหลือใน production ก่อน migration รันจริง
- รายการ 3 ไม่เปิด server-side enforcement จนกว่า build ที่มี field นี้ถูกปล่อยจริง
- รายการ 4 ผ่าน safety-chain checklist ทั้ง 5 ข้อในหัวข้อ 7 ก่อน bump และคอมเมนต์เตือนตรงกับพฤติกรรมจริง
- รายการ 6 ยืนยันอายุ token ใหม่ถูกต้องจากการ decode จริง ไม่ใช่แค่อ่านค่า config
- รายการ 7 ผ่าน acceptance tests ในหัวข้อ 10 ครบ รวมการรันเทียบฐานข้อมูลจริง/staging อย่างน้อยหนึ่งรอบ
- commit แยกตามรายการ ไม่ปนไฟล์ที่ไม่เกี่ยวข้อง ไม่แตะไฟล์ untracked เดิมของ repo

Compile ผ่านเพียงอย่างเดียวไม่ถือว่าเสร็จ โดยเฉพาะรายการ 2 และ 7 ที่ต้อง verify กับฐานข้อมูล/อุปกรณ์จริงก่อน production

## 13. รูปแบบรายงานเมื่อส่งมอบ

ให้รายงาน:

1. สรุปพฤติกรรมก่อนและหลังของทั้ง 7 รายการ
2. รายการไฟล์ Android/backend ที่แก้ แยกตามรายการ
3. Room version และ migration ที่เพิ่ม (ถ้ามี) จากเท่าไรไปเท่าไร
4. ผลตรวจ safety chain ของรายการ 4 ก่อน/หลัง bump
5. นิยาม trigger จริงที่ใช้เขียน migration ของรายการ 7 (อ้างแหล่งที่มา ไม่ใช่เดา)
6. tests ที่รัน พร้อมจำนวนผ่าน/ล้มเหลว แยก unit/instrumented/staging
7. known limitations ที่ยังไม่ verify กับของจริง (เช่น migration ที่เขียนแต่ไม่ได้รันบนอุปกรณ์จริง)
8. deployment state (push/ไม่push, deploy/ไม่deploy)
9. งานที่ยังไม่ผ่าน production gate

ห้ามรายงานว่าเสร็จ หากรายการ 2 หรือ 7 ยังไม่ได้ทดสอบกับฐานข้อมูล/อุปกรณ์จริง ให้ใช้คำว่าเสร็จระดับโค้ดและระบุ gate ที่ค้างอย่างตรงไปตรงมา
